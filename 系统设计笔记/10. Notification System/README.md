# 第10章：设计一个通知系统

## 引言
**通知系统**是现代应用不可或缺的组成部分，能够提供及时的产品通知、活动、优惠和提醒等信息。通知可以通过以下方式发送：
1. **推送通知**（移动端或桌面端），
2. **短信**，以及
3. **电子邮件**。

本章重点讨论如何设计一个可扩展的系统，能够每天发送数百万条通知。

---

## 第1步：理解问题
### 需求
- **通知类型：** 推送通知、短信和电子邮件。
- **交付方式：** 软实时系统，延迟最小。
- **平台：** iOS、Android 和桌面端。
- **触发方式：** 通知可以由客户端应用触发，也可以由服务器端定时任务触发。
- **规模：**
  - **推送通知：** 每天 1000 万条，
  - **短信：** 每天 100 万条，
  - **电子邮件：** 每天 500 万封。
- **退订支持：** 用户可以禁用特定类型的通知。

---

## 第2步：高层设计

### 组件

1. **通知类型：**
   - **iOS 推送通知：** 使用 **Apple Push Notification Service (APNS)**。
   - **Android 推送通知：** 使用 **Firebase Cloud Messaging (FCM)**。
   - **短信：** 使用 Twilio 或 Nexmo 等第三方服务。
   - **电子邮件：** 使用 SendGrid 或 Mailchimp 等商业邮件服务。

2. **联系方式收集：**
   <div style="margin-left:3rem">
      <img src="./images/contact-info-gathering.png" alt="Contact Info Gathering" width="500">
   </div>

   - 在应用安装或注册时收集设备令牌、电话号码或电子邮件地址。
   - 将联系方式存储在数据库中：
     - **设备令牌表：** 用于推送通知。
     - **用户表：** 用于电子邮件和电话号码。


3. **通知发送流程：**

   <div style="margin-left:3rem">
      <img src="./images/high-level-design.png" alt="High Level Design" width="500">
   </div>

   - **触发服务：**
      - 生成事件以启动通知（如账单提醒、物流更新）。
      - 可以是微服务、定时任务或分布式系统，用于触发通知发送事件。
   - **通知服务器：**
      - 提供 API 供服务发送通知。
      - 执行基本验证，如校验电子邮件和电话号码。
      - 查询数据库或缓存，获取渲染通知所需的数据。
   - **第三方服务：** 将通知发送给用户。


### 初始设计中的挑战
- **单点故障（SPOF）：** 一台通知服务器崩溃可能导致整个系统瘫痪。
- **可扩展性问题：** 难以独立扩展数据库、缓存和处理组件。
- **性能瓶颈：** 发送通知对资源需求很高。

### 改进设计

   <div style="margin-left:3rem">
      <img src="./images/improved-design.png" alt="Improved Design" width="500">
   </div>

- 将数据库和缓存从通知服务器中分离出来。
- 引入**横向扩展**，部署多台通知服务器。
- 使用**消息队列**解耦系统组件。
   - 消息队列在需要发送大量通知时充当缓冲区。
- 添加工作节点，从消息队列中拉取通知事件并发送给对应的第三方服务。


---

## 第3步：深入设计

### 可靠性
1. **防止数据丢失：**
   <div style="margin-left:3rem">
   <img src="./images/data-loss.png" alt="Data Loss" width="400">
   </div>

   - 将通知数据持久化到数据库，并实现重试机制。
   - 引入通知日志数据库用于数据持久化。


2. **去重：**
   - 检查事件 ID 以避免发送重复通知。
   - 当通知事件首次到达时，通过检查事件 ID 判断是否已处理过。
   如果已处理则丢弃，否则发送通知。


### 附加组件
   <div style="margin-left:3rem">
   <img src="./images/events-tracking.png" alt="Events Tracking" width="400">
   </div>

1. **通知模板：** 预定义模板，确保通知的一致性和高效性。
2. **通知设置：**
   - 用户可以选择启用或禁用特定渠道（推送、短信或邮件）。
   - 存储在专用的通知设置表中。
3. **限流：** 限制发送给用户的通知频率。
4. **重试机制：** 当第三方服务失败时，重试发送通知。
5. **队列监控：** 跟踪排队中的通知，动态扩展工作节点。
6. **事件追踪：** 收集打开率、点击率和参与度等指标。


### 安全性
- 使用 **AppKey** 和 **AppSecret** 对推送通知 API 进行身份验证和安全保护。

### 通知流程

   <div style="margin-left:3rem">
   <img src="./images/updated-design.png" alt="Updated Design" width="500">
   </div>

1. 触发服务调用 API 发送通知。
2. 通知服务器验证请求，并从缓存或数据库中获取元数据。
3. 通知事件被发送到消息队列。
4. 工作节点处理事件并与第三方服务交互。
5. 第三方服务将通知发送给用户。


## 关键优化
1. **水平扩展：** 增加更多通知服务器以实现负载分发。
2. **消息队列：** 解耦处理流程以应对高吞吐量。
3. **缓存：** 通过缓存频繁访问的数据来降低延迟。
4. **分布式爬取：** 按地理位置优化消息投递以提升性能。
