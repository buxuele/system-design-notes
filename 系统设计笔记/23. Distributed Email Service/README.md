# 第23章：分布式邮件服务

## 引言

本章我们将设计一个**分布式邮件服务**，类似于**Gmail**。

2020年，**Gmail** 拥有18亿活跃用户，而 **Outlook** 在全球拥有4亿用户。

---

## 第1步：理解问题并确定设计范围

- C：有多少用户使用该系统？
- I：10亿用户
- C：我认为以下功能很重要——身份验证、发送/接收邮件、获取邮件、过滤邮件、搜索邮件、反垃圾邮件保护。
- I：很好的清单。现在先不用担心身份验证。
- C：用户如何连接邮件服务器？
- I：通常，邮件客户端通过 SMTP、POP、IMAP 连接，但本问题中我们将使用 HTTP。
- C：邮件可以包含附件吗？
- I：可以

### **非功能性需求**

- **可靠性** —— 我们不应丢失数据
- **可用性** —— 我们应使用复制来防止单点故障。同时应能容忍部分系统故障。
- **可扩展性** —— 随着用户规模增长，系统应能应对。
- **灵活性与可扩展性** —— 系统应灵活且易于扩展新功能。我们选择 HTTP 而非 SMTP/其他邮件协议的原因之一。

### **粗略估算**

- **10亿用户**
- 假设每人每天发送10封邮件 → **每秒10万封邮件**。
- 假设每人每天接收40封邮件，每封邮件平均有50KB元数据 → **每年730PB存储**。
- 假设20%的邮件带有存储附件，平均大小为500KB → **每年1460PB**。

## 第2步：提出高层设计并获得认可

### **邮件基础知识**

用于发送和接收邮件的协议有多种：
- **SMTP** —— 从一个服务器向另一个服务器发送邮件的标准协议。
- **POP** —— 从远程邮件服务器接收并下载邮件到本地客户端的标准协议。邮件一旦被检索，就会从远程服务器删除。
- **IMAP** —— 类似于 POP，用于从远程服务器接收和下载邮件，但它会将邮件保留在服务器端。
- **HTTPS** —— 严格来说不是邮件协议，但可用于基于 Web 的邮件客户端。

除了邮件协议，我们还需要为邮件服务器配置一些 DNS 记录——MX 记录：

    <img src="./images/dns-lookup.png" alt="dns-lookup" width="500" />
</div>

邮件附件以 Base64 编码发送，大多数邮件服务通常有25MB的大小限制。
这是可配置的，因个人账户与企业账户而异。

### **传统邮件服务器**

当用户数量有限且连接到单一服务器时，传统邮件服务器工作良好。

<div style="margin-left:3rem">
    <img src="./images/traditional-mail-server.png" alt="traditional-mail-server" width="500" />
</div>

- Alice 登录她的 Outlook 邮箱并点击"发送"。邮件通过 SMTP 发送到 Outlook 邮件服务器。
- Outlook 服务器查询 DNS 以找到 gmail.com 的 MX 记录，并将邮件传输到其服务器。通信通过 SMTP 进行。
- Bob 通过 IMAP/POP 从他的 Gmail 服务器获取邮件。

在传统邮件服务器中，邮件存储在本地文件系统上。每封邮件都是一个独立的文件。

<div style="margin-left:3rem">
    <img src="./images/local-dir-storage.png" alt="local-dir-storage" width="500" />
</div>

随着规模的增长，磁盘 I/O 成为瓶颈。此外，它也无法满足我们的高可用性和可靠性要求。磁盘可能损坏，服务器可能宕机。

### **分布式邮件服务器**

分布式邮件服务器旨在支持现代用例并解决现代可扩展性问题。

这些服务器仍然可以支持 IMAP/POP 以供原生邮件客户端使用，以及 SMTP 用于服务器间的邮件交换。

但对于功能丰富的基于 Web 的邮件客户端，通常使用基于 HTTP 的 RESTful API。

示例 API：
- `POST /v1/messages` —— 向 To、Cc、Bcc 头部中的收件人发送消息。
- `GET /v1/folders` —— 返回电子邮件账户的所有文件夹。

示例响应：

```
[{id: string        唯一文件夹标识符。
  name: string      文件夹名称。
                    根据 RFC6154 [9]，默认文件夹可以是以下之一：
                    All、Archive、Drafts、Flagged、Junk、Sent、
                    和 Trash。
  user_id: string   引用账户所有者
}]
```

- `GET /v1/folders/{:folder_id}/messages` —— 返回某个文件夹下的所有消息，支持分页。
- `GET /v1/messages/{:message_id}` —— 获取特定消息的所有信息。

示例响应：

```
{
  user_id: string                      // 引用账户所有者。
  from: {name: string, email: string}  // 发送者的 <姓名, 邮箱> 对。
  to: [{name: string, email: string}]  // <姓名, 邮箱> 对的列表
  subject: string                      // 邮件主题
  body: string                         // 邮件正文
  is_read: boolean                     // 指示消息是否已读。
}
```

以下是分布式邮件服务器的高层设计：

<div style="margin-left:3rem">

- **Webmail** - 用户使用网页浏览器发送/接收邮件
- **Web 服务器** - 面向公众的请求/响应服务，用于管理登录、注册、用户资料等
- **实时服务器** - 用于向客户端实时推送新邮件更新。我们使用 WebSocket 进行实时通信，但对于不支持 WebSocket 的旧版浏览器，则回退到长轮询
- **元数据数据库** - 存储邮件元数据，如主题、正文、发件人、收件人等
- **附件存储** - 对象存储（例如 Amazon S3），适合存储大文件
- **分布式缓存** - 我们可以将最近收到的邮件缓存到 Redis 中，以提升用户体验
- **搜索存储** - 分布式文档存储，用于支持全文搜索

以下是邮件发送流程：

<div style="margin-left:3rem">
    <img src="./images/email-sending-flow.png" alt="email-sending-flow" width="500" />
</div>

- 用户撰写邮件并点击"发送"。邮件被发送到负载均衡器。
- 负载均衡器对过量发送进行限流，并将邮件路由到其中一台 Web 服务器。
- Web 服务器进行基础邮件验证（例如邮件大小），如果域名与发件人相同则短路外部发送流程。但会先进行垃圾邮件检查。
- 如果基础验证通过，邮件被发送到消息队列（附件从对象存储中引用）。
- 如果基础验证失败，邮件被发送到错误队列。
- SMTP 发送工作者从出站队列中拉取消息，执行垃圾邮件/病毒检查，然后路由到目标邮件服务器。
- 邮件存储在"已发送邮件"文件夹中。

我们还需要监控出站消息队列的大小。队列增长过大可能意味着存在问题：
- 收件人的邮件服务器不可用。我们可以使用指数退避策略在稍后时间重试发送邮件。
- 消费者数量不足以处理负载，可能需要扩展消费者。

以下是邮件接收流程：

<div style="margin-left:3rem">
    <img src="./images/email-receiving-flkow.png" alt="email-receiving-flow" width="500" />
</div>

-  incoming 邮件到达 SMTP 负载均衡器。邮件被分发到 SMTP 服务器，在其中执行邮件接收策略（例如无效邮件直接丢弃）。
- 如果邮件附件过大，我们可以将其放入对象存储（S3）。
- 邮件处理工作者进行初步检查，之后邮件被转发到存储、缓存、对象存储和实时服务器。
- 离线用户在他们重新上线后通过 HTTP API 获取新邮件。

## 第3节：设计深入解析

现在让我们更深入地了解其中一些组件。

### **元数据数据库**

以下是邮件元数据的一些特征：
- 头部通常较小且被频繁访问
- 正文大小从小到大不等，但通常只读取一次
- 大多数邮件操作都局限于单个用户——例如获取邮件、标记为已读、搜索等
- 数据的新颖性会影响数据的使用。用户通常只阅读最近的邮件
- 数据具有高可靠性要求。数据丢失是不可接受的

在 Gmail/Outlook 的规模下，数据库通常是自研的，以减少每秒输入/输出操作（IOPS）。

让我们考虑一下有哪些数据库选项：
- **关系型数据库** - 我们可以为头部和正文建立索引，但这些数据库通常针对小块数据进行了优化。
- **分布式对象存储** - 这可能是备份存储的一个不错选择，但无法高效地支持搜索/标记为已读等操作。
- **NoSQL** - Google BigTable 被 Gmail 使用，但它并未开源。

基于以上分析，很少有现有方案能够完美契合我们的需求。
在面试场景中，设计一个全新的分布式数据库解决方案是不现实的，但需要提及以下特征：
- 单个列可以是几 MB 的大小
- 强数据一致性
- 旨在减少磁盘 I/O
- 高可用性和容错性
- 应易于创建增量备份

为了对数据进行分区，我们可以使用 `user_id` 作为分区键，使得一个用户的数据存储在单个分片上。
这会阻止我们与多个用户共享一封邮件，但这不是本次面试的要求。

让我们来定义这些表：
- 主键由分区键（数据分布）和聚簇键（数据排序）组成
- 我们需要支持的查询——获取用户的所有文件夹、显示某个文件夹中的所有邮件、创建/获取/删除一封邮件、获取已读/未读邮件、获取对话线程（加分项）

### **邮件投递**

搭建一台发送邮件的服务器很容易，但让邮件到达收件人的收件箱却很困难，因为存在垃圾邮件防护算法。

如果我们只是搭建一台新的邮件服务器并开始通过它发送邮件，我们的邮件很可能会被放进垃圾邮件文件夹。

为了防止这种情况，我们可以这样做：
- **专用 IP** —— 使用专用 IP 发送邮件，否则收件方服务器不会信任你。
- **分类邮件** —— 避免在同一台服务器上发送营销邮件，以防止更重要的邮件被归类为垃圾邮件。
- **缓慢预热 IP 地址** —— 逐步与大型邮件服务商建立良好信誉。预热一个新 IP 需要 2 到 6 周。
- **快速封禁垃圾邮件发送者** —— 以免损害你的信誉。
- **反馈处理** —— 与互联网服务提供商（ISP）建立反馈循环，持续跟踪投诉率并快速封禁垃圾邮件账户。
- **邮件认证** —— 使用常见技术来抵御钓鱼攻击，例如发件人策略框架（SPF）、域名密钥识别邮件（DKIM）等。

你不需要记住所有内容。只需知道，构建一台优秀的邮件服务器需要大量的领域知识。

### **搜索**

搜索包括基于邮件内容的全文搜索，以及基于发件人、收件人、主题、是否已读等过滤条件的高级查询。

邮件搜索的一个特点是：它局限于用户本地，且写操作多于读操作，因为每次操作都需要重新建立索引，但用户很少使用搜索标签页。

让我们对比 Google 搜索与邮件搜索：

|               | 范围                 | 排序方式                            | 准确性                                          |
|---------------|----------------------|-------------------------------------|-------------------------------------------------|
| Google 搜索   | 整个互联网           | 按相关性排序                        | 索引建立需要一定时间，因此结果不是即时的。      |
| 邮件搜索      | 用户自己的邮箱       | 按属性排序，例如时间、日期等        | 索引应快速建立，且结果准确。                    |

为了实现这一搜索功能，一个选择是使用 Elasticsearch 集群。我们可以使用 `user_id` 作为分区键，将数据归组到同一节点下：

</div>

变更操作通过 Kafka 异步执行，以将服务与重新索引流程解耦。实际上，搜索数据是同步进行的。

Elasticsearch 是最流行的搜索引擎数据库之一，对邮件的全文搜索支持非常好。

另外，我们也可以尝试开发自定义的搜索方案来满足特定需求。

设计这样的系统超出了本文范围。构建它的核心挑战之一是优化写密集型工作负载。

为此，我们可以使用日志结构合并树（Log-Structured Merge-Trees，LSM）来组织磁盘上的索引数据。写路径仅针对顺序写入进行优化。
该技术被应用于 Cassandra、BigTable 和 RocksDB。

其核心思想是将数据存储在内存中，直到达到预设阈值，然后再合并到下一层（磁盘）：

<div style="margin-left:3rem">
    <img src="./images/lsm-tree.png" alt="lsm-tree" width="500" />
</div>

两种方案之间的主要权衡：
- Elasticsearch 在一定程度上可扩展，而自定义搜索引擎可以针对邮件使用场景进行微调，从而支持更大的扩展。
- Elasticsearch 是我们需要独立维护的额外服务，与元数据存储并存。自定义方案可以本身就是数据存储。
- Elasticsearch 是现成的解决方案，而自定义搜索引擎需要大量的工程投入来构建。

## 第4步：总结

补充讨论要点：
- **容错性** - 系统的许多部分都可能发生故障，值得深入研究我们如何处理节点故障。
- **合规性** - 考虑到欧洲的 GDPR 法规，个人身份信息（PII）需要以合理的方式存储。
- **安全性** - 邮件加密、反钓鱼保护、安全浏览等。
- **优化** - 例如防止不同用户多次发送相同附件的重复问题。
